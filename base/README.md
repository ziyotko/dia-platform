# Base 底座系统

Base 是一个可落地的「管理后台底座平台」，用于将任意已有的 `frontend + backend` 系统作为子应用统一接入、管理、运营。

## 定位

- 底座平台本身提供：统一登录、租户、应用注册、用户/角色/权限、菜单、审计日志、系统设置、消息通知、文件管理、流程角色（工作流）、图形验证码与接口限流。
- 已有系统（子应用）按标准接入后，底座负责鉴权、菜单聚合、路由分发、权限校验、日志审计。
- 未来可通过插件/适配器机制横向扩展新能力，无需改动底座核心。

## 技术栈

- 后端：Go 1.21 + Gin + GORM + MySQL + Redis
- 前端：Vue 3.4 + Vite 5 + Element Plus 2.6 + Pinia 2.1 + TypeScript 5.4

## 目录结构

```
base/
├── backend/          # 底座后端（Go + Gin + GORM）
├── frontend/         # 底座前端（Vue 3 + Vite）
├── integration/      # 子应用接入标准与 SDK/适配器示例
└── README.md
```

## 快速开始

### 1. 启动后端

```bash
cd base/backend

# 修改 config.yaml 中的 MySQL/Redis 配置
# 确保数据库已存在

go mod tidy
go run cmd/server/main.go
```

服务默认监听 `:8080`，首次启动会自动创建：

- 超级管理员：`admin / admin123`
- 底座默认菜单（控制台、系统管理、消息管理、工作流管理及其子菜单：流程角色 / 流程定义 / 流程实例 / 我的待办）
- 默认超级管理员角色，并关联所有底座菜单与全部接口权限点
- 底座接口权限点（`base_permission`，幂等写入，按 `code` 去重，重启不会重复插入）
- 菜单初始化幂等：已存在的菜单不会被重建，仅补齐缺失项；不会覆盖管理员在后台的调整

> 种子数据在每次启动时幂等执行，因此修改代码后 **重启后端** 即可生效。
> 早期版本初始化过的四个占位菜单（流程模型/流程实例/审批任务/流程设计器）在启动时会自动清理，避免点击后落到 404。

可选参数：

```bash
go run cmd/server/main.go -mock-data    # 额外插入模拟机构数据（本地测试）
```

### 2. 启动前端

```bash
cd base/frontend
npm install
npm run dev
```

默认访问 `http://localhost:3000/base/`，登录 admin / admin123。

## 核心概念

| 概念 | 说明 |
|------|------|
| 租户（Tenant） | 平台中的组织单位，用户、应用实例均归属租户 |
| 应用（App） | 一个可被接入的子系统，记录名称、编码、前端入口、后端入口、接入方式（iframe/proxy） |
| 应用实例（AppInstance） | 应用在租户下的开通实例，控制哪些租户能用哪些应用 |
| 用户（User） | 底座平台用户，支持多租户上下文 |
| 角色（Role） | 角色绑定权限点和菜单 |
| 菜单（Menu） | 底座菜单 + 各应用上报/注册的菜单树 |
| 权限（Permission） | 接口级权限点，基于 HTTP Method + Path 匹配，可在「权限管理」中维护；前端按钮按同一权限标识控制显隐 |
| 适配器（Adapter） | 子应用按标准实现适配器，底座即可识别并代理/跳转 |
| 流程角色（WorkflowRole） | 审批职责的集合（如审核组/复审组），与系统角色解耦，只决定「谁能审批」 |
| 流程定义（Workflow） | 一条审批链路：由若干按顺序执行的审批节点组成 |
| 流程实例（WorkflowInstance） | 一次具体的审批（发起人 + 标题 + 业务单据），按节点推进 |
| 审批任务（WorkflowTask） | 落在某个审批人身上的待办，处理后节点推进或流程结束 |

## 工作流

底座内置一条可落地的审批流程引擎，由四个菜单组成：

| 菜单 | 作用 | 面向人群 |
|------|------|----------|
| 流程角色 | 定义审批角色（如审核组）并配置成员 | 管理员 |
| 流程定义 | 定义流程并编排审批节点（顺序、审批人类型） | 管理员 |
| 流程实例 | 发起流程、查看进度与流转记录、撤销/删除 | 所有用户（普通用户只看自己发起的） |
| 我的待办 | 待我审批 / 我已处理，支持通过、驳回与审批意见 | 所有用户 |

引擎语义（刻意保持简单、可预测）：

- 节点按 `排序` **串行**执行；同一节点内多个审批人为**或签**（任一人处理即代表该节点完成，其余待办自动失效）。
- 节点审批人支持三种来源：**流程角色**（角色成员或签）、**指定用户**、**发起人本人**。
- 节点解析不到有效审批人（角色无成员 / 用户被删除或停用）时**自动通过**并写入流转日志，避免流程被永久挂起。
- 全部节点通过 → 实例「已通过」；任一节点驳回 → 实例「已驳回」且其余待办失效；发起人（或管理员）可撤销审批中的实例。
- 每个实例都保留完整的**流转记录**（发起 / 通过 / 驳回 / 撤销 / 自动通过 / 完成），详情页以时间线展示。

隔离与权限：

- 流程角色、流程定义、流程实例、审批任务均带 `tenant_id`，**严格按租户隔离**（不像菜单/消息那样可见平台级数据）；平台超管可跨租户管理与查看。
- 流程角色成员、流程节点审批人必须与角色/流程同租户。
- 流程定义（含节点编排）由管理员维护（`base:workflow-def:*`）；发起、我的申请、待办审批属于「自己的数据」，普通登录用户即可使用，归属校验在服务层完成（只能操作自己发起或自己负责的任务）。
- 与业务系统的对接：`businessType` + `businessId` 用于标记流程关联的业务单据，子应用可将其审批结果回写业务状态。

## 接入方式

1. **IFrame 接入**：子应用独立部署，底座通过 iframe 嵌入，统一传 token/租户信息（URL 自动追加 `base_token`、`user_id`、`username`、`tenant_id`）。
2. **API 代理接入**：子应用后端被底座反向代理，底座在请求头中注入用户信息，并自动拼接应用配置的 `API 前缀`。

详见 [integration/README.md](./integration/README.md)。

## 消息通知

- 消息通道仅支持 `站内信（in-app）` 与 `邮件（email）`；邮件为通知型通道，需选定具体收件人，不支持广播。
- 站内信支持收件箱/发件箱、已读/未读筛选与「全部标为已读」。
- 广播消息（`receiver_id = 0`）在库中只有一行，**已读状态按人记录**在 `base_message_read`（否则一个人已读会让所有人的未读红点一起消失）；定向消息仍用 `base_message.is_read`。因此广播消息不支持由单个接收者删除（仅发送者或管理员可删）。
- 定向发送只允许发给同租户的启用用户（站内信与邮件同一口径），避免跨租户投递。

## 安全与隔离

- 所有登录接口均经过 JWT 认证、操作审计、接口级权限校验。
- 超级管理员（`tenantID == 0`）可跨租户管理；租户管理员（`is_admin`）在本租户内拥有全部权限；普通用户按角色分配的权限点校验，未分配权限时除白名单接口（个人信息/菜单/权限标识/改密/仪表盘/我的应用/未读数/工作流中属于自己的数据）外一律拒绝，需管理员在「角色管理 → 分配权限」中授权。
- 普通租户的数据按 `tenant_id` 隔离；平台超管可在列表页通过「所属租户」筛选查看各租户数据。
- 字典、机构、消息模板、菜单、消息这些「平台预置 + 租户自建」的数据，租户可读取自己的或平台共用的（`tenant_id = 自身 OR tenant_id = 0`）；用户、角色、文件、应用实例则严格按租户隔离。
- 生产环境请在 `config.yaml` 的 `server.trusted_proxies` 中配置可信反代地址，否则限流按 `RemoteAddr` 计算（防止伪造 `X-Forwarded-For` 绕过限流）。
- 详见 [backend/docs/security.md](./backend/docs/security.md)。

## 与现有 caam-portal 整合建议

1. 保持现有 `frontend/` 和 `backend/` 不变，独立运行。
2. 在 Base 后台「应用管理」注册：`code=caam-portal`、`type=proxy`、`backendUrl=http://localhost:8080`。
3. 在「应用实例」中为租户开通该应用。
4. 在「菜单管理」添加 `appCode=caam-portal` 的菜单，`target` 设为 `iframe` 并填写现有 frontend 地址。
5. 用户即可从 Base 平台一站式访问 caam-portal。
